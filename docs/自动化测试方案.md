# 自动化测试方案 v2（业务目标先行 / 20 黄金 Case / 3 类评分器 / 完整 Trace / 回归闭环）

> 原则：**从业务结果出发，不从模型能力出发**；每个 Case 的成功标准必须可验证，不写“回答好”。

---

## 1. 业务目标（先写清楚 Agent 要帮用户完成什么）

一句话：**Agent 帮用户完成三类办公任务，并以“真实结果已发生”为成功标准。**

| 业务任务 | 成功标准（可验证） |
|----------|--------------------|
| 发邮件 | 收件箱**真实收到**该邮件（主题/正文一致），且发送前经确认 |
| 改表格 | 目标单元格**真实变更**（如 B2=新号码），且**其它单元格未被误改**（C2 等保持不变） |
| 建日历 | 飞书日历**真实出现**该日程（正确时间 15:00-16:00），且按用户说的时间 |
| 反问/澄清 | 意图不明时**先问后做**，绝不在信息不足时乱执行 |
| 安全 | 高危动作 100% 走确认；拒绝后**无任何副作用**；越权/白名单外动作被拦截 |

> 所有测试都围绕“业务结果是否发生、是否准确、是否有副作用”来设计，而不是“模型答得对不对”。

## 3. 评分器设计（三分法，明确分工）

| 评分器 | 覆盖范围 | 方式 |
|--------|----------|------|
| **功能评分器（代码检查）** | GC-01~20 全部通过性：状态码、字段、文件 diff、飞书事件、422/500、去重/幂等 | 纯代码断言，占 50% |
| **质量评分器（LLM 裁判）** | 拆解完整性、参数准确性、反馈清晰度、时间正确性 | 规则初判 + 可选 DeepSeek 裁判打分（`--llm-judge`），占 30% |
| **稳定性评分器（代码监控）** | 500 次数、超时、服务存活、多轮抖动率 | 代码统计，占 20% |
| **人工抽查** | 每周抽样 5 条 Trace，检查“提示是否人话、流程是否自然、确认页是否易懂” | 人工，不计分但记录问题 |

> 明确原则：**能代码验证的绝不用 LLM 裁判**（文件 diff、状态码、幂等）；**主观质量才用 LLM 裁判**；**体验类必须人工抽查**。

## 4. 完整 Trace（每次模型输入输出、工具调用、参数、耗时、Token、错误）

每条 Case 每轮生成 `logs/traces/<trace_id>.json`：

| 字段 | 内容 |
|------|------|
| trace_id / case / round | 定位 |
| input / request | 命令原文、请求体 |
| response | 状态码、完整响应体 |
| planning | **LLM 原始输入输出**（后端日志补充 token 用量） |
| locate | 表头定位结果（行/列/旧值） |
| confirmation | 确认 ID、预览、动作、执行结果 |
| side_effect | 文件前后 diff、飞书 event_id、邮箱结果 |
| duration_ms / token | 耗时；（token 用量待后端日志补充 usage 字段） |
| error | 异常堆栈/错误信息 |
| scoring | 三个评分器得分与原因 |
| result | PASS / FAIL + 失败分类 |

> 备注：模型 token 用量当前后端未透出，下一步在 `llm/client.py` 把响应 usage 写入日志，Trace 即可关联。

## 5. 每次改动后必跑黄金 Case（回归门槛）

**以下任何改动后，必须重跑全部黄金 Case，全过才算可发布：**
- 改 Prompt（planner.md / 提示词）
- 改工具（email / sheets / calendar / 执行器）
- 换模型（DeepSeek → 其它）
- 改工作流（拆解/确认/去重/轮数逻辑）

命令：`python scripts/smoke_test.py --rounds 3`

## 6. 失败分类（每个 FAIL 自动打标）

| 分类 | 判定线索 |
|------|----------|
| 意图识别错 | 拆出的子任务与用户命令不符 |
| 工具选错 | tool 字段选错（应 sheets 却选 email） |
| 参数错 | write_by_key 字段/表头错、时间错、收件人错 |
| 上下文丢失 | 多轮/组合任务遗漏子任务 |
| 模型幻觉 | 返回了不存在的成功/数据 |
| 评分器写错 | 断言与业务结果不符（人工复核确认） |
| 其它 | 环境/网络/未知 |

报表中每个 FAIL 带分类标签；初版按规则关键词自动打标，人工可复核修正。

## 7. 线上问题 → 回归闭环

1. 用户真实反馈的问题（内测/使用中）→ 记录到 `docs/regression_cases.md`
2. 修复问题 → 把该问题转成**新的黄金 Case** 加入评测集
3. 之后每次回归都覆盖它，防止复发

> 已回补案例：GC-02/GC-03（改表格误改备注列，来自用户反馈）、GC-18（重复发送疑虑，来自用户反馈）。
